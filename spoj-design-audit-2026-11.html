What to preserve

  • The map + sheet architecture and its desktop results sidebar.
  • Warm Ember neutrals, consistent rounded controls, transport-mode colours and tabular number typography.
  • Planned versus expected times, delay labels, platform information and stop-by-stop journey detail.
  • Automatic light/dark appearance, theme previews and the map contrast setting. Settings fit the inspected 320px viewport without horizontal overflow.

Prioritised improvements

P1: directly affects completing or trusting a core task. P2: improves access, discovery or repeated use. Relative effort varies by implementation; priorities reflect user impact.

P1 · Browser + source

1. Make search explain what is happening

Search results load successfully, but the panel provides no explicit loading, error or no-match state. The search hook suppresses request failures. A blank list cannot explain whether the query failed or found nothing.

Improve: Keep existing results during refresh, but add a subtle “Hľadám…” status. On zero matches, show “Nenašli sme žiadne výsledky” and a suggestion to change the query. On failure, retain the query and offer “Skúsiť znova”. Distinguish partial stop/place availability.

Done when: A slow request, an unmatched query and a failed request each produce a distinct, announced state with a useful next step.

Evidence: src/data/useSearch.ts:39; src/features/transit/TransitScreen.tsx:2340

P1 · Browser + source

2. Give the primary action to something that works

The wallet button is actionable but calls an empty handler. Journey cards and details feature a bright green “🚧 — €” placeholder; tracking is a quieter secondary button. The strongest visual affordance promises unavailable functionality.

Improve: Hide the wallet until it works. Replace the fare button with secondary text such as “Cena nie je dostupná”, or omit it. Make “Sledovať cestu” the primary action where tracking is supported, with a short explanation of what it enables.

Done when: Every button responds meaningfully; unavailable fares never appear as a primary action.

Evidence: src/features/transit/TransitScreen.tsx:1555; src/features/transit/TransitScreen.tsx:3202

P1 · Browser + source

3. Compare the whole journey

The inspected Hlavná stanica → Trnavské mýto option shows “3 min” beside 5 minutes of access walking and 4 minutes after alighting. The headline duration describes the vehicle segment, leaving users to calculate at least about 12 minutes of travel, before any waiting.

Improve: Show an estimated door-to-door duration, leave-by time and arrival at the actual destination. Keep boarding/alighting times as secondary facts. Label walking as estimated, show walking total and transfer count, and make the service date clear when the next connection is tomorrow.

Done when: A user can compare options and know when to leave without adding the legs themselves.

Evidence: src/features/transit/TransitScreen.tsx:2539

P1 · Browser accessibility tree + source

4. Make the core flow operable with a keyboard

Suggestion rows render as generic clickable elements while bookmark controls have button semantics. Departure rows also omit an explicit button role. The search input removes its outline; the list lacks combobox semantics and explicit arrow/Enter selection.

Improve: Use correct action semantics, visible focus and predictable tab order. Give autocomplete a named combobox/listbox pattern with Arrow keys, Enter and Escape. Keep saving a favourite separate from selecting a result.

Done when: A keyboard-only user can choose both endpoints, inspect an option and return; focus is always visible. Validate with a screen reader before claiming accessibility conformance.

Evidence: src/features/search/SuggestionRow.tsx:26; src/features/transit/TransitScreen.tsx:2309; src/features/transit/TransitScreen.tsx:3809

P2 · Browser dimensions + source

5. Keep compact visuals, enlarge effective targets

Favourite pills are 34px high and time/filter chips are 32px. Mobile favourite editing depends on long press, which has no visible cue. The desktop edit affordance is 22 × 26px. Main map controls already provide a better 48px precedent.

Improve: Use a 44 × 44px minimum effective target as a product standard, with spacing to prevent overlap. Retain smaller pill artwork if desired. Add an obvious favourites management or overflow action that also works on narrow desktop windows.

Done when: All frequent actions have comfortable, separate targets; editing is discoverable without a long press or hover.

Evidence: src/features/favourites/FavouritesRow.tsx:9; src/features/favourites/FavouritesRow.tsx:34; src/features/transit/TransitScreen.tsx:3884

P2 · Source review

6. Explain the sheet and carousel controls

The sheet handle is decorative and controlled by pan responders; carousel dots are decorative too. The same surface switches between a carousel and a list as the sheet changes height. This is efficient once learned but gives newcomers little guidance.

Improve: Make the handle a named expand/collapse control with current state. Add “Zobraziť všetky” and accessible previous/next actions with “2 z 5” context. Preserve selection when switching layouts.

Done when: The complete content can be reached without dragging or swiping, and the current position is announced.

Evidence: src/features/transit/TransitScreen.tsx:1096; src/features/transit/TransitScreen.tsx:2144

P2 · Measured token contrast + source

7. Strengthen small secondary text

Ember tertiary text #958491 on #fbfaf9 measures 3.36:1; Classic #8a969d on #f9fafb measures 2.90:1. These tokens appear in 12px disclaimer and arrival-note text, below the 4.5:1 normal-text contrast target. Main Ember secondary text is healthier at 5.48:1.

Improve: Darken tertiary text in light themes to at least 4.5:1 wherever it carries information. Reserve low contrast for decoration. Prefer 14px for useful supporting information, and verify text zoom and dynamic type.

Done when: Both palettes meet text contrast targets on actual surfaces; larger text does not clip critical names or times.

Evidence: src/theme/palette.ts:30; src/features/transit/TransitScreen.tsx:4004

P2 · Browser + source

8. Use the desktop width for the task

A permanent 300px rail holds the brand and a short description on the inspected 1440px desktop layout. The app already has a 400px results sidebar, leaving less room for the useful map. The brand rail is appropriate for a pitch but contributes little during route planning.

Improve: Keep the explanatory rail in pitch mode. In ordinary use, move branding into a compact header or About surface and give the width to the map or a wider route comparison panel.

Done when: The normal desktop layout prioritises results and map; pitch context remains available on proposal links.

Evidence: app/+html.tsx:141; src/platform/useDesktopLayout.ts:5

P2 · Source review

9. Respect motion preferences

Sheet transitions use fixed animation durations; several sheet/carousel animations have no app-level reduced-motion handling. Motion clarifies spatial relationships, but should be optional.

Improve: Read the platform reduced-motion preference. Replace long slides, springs and pulses with immediate changes or brief fades; keep focus and state transitions intact.

Done when: Enabling reduced motion removes nonessential movement without removing information or controls.

Evidence: src/features/sheet/ModalSheet.tsx:7; src/features/transit/TransitScreen.tsx:3526

Observed examples

Suggested implementation order

  1. Trust and task completion: search states, working primary actions, door-to-door timing.
  2. Access: keyboard flow, touch targets, contrast, visible sheet controls and reduced motion.
  3. Refinement: desktop space, favourites management and shorter, outcome-based settings copy.

Validate each change on the complete flow: choose endpoints → compare options → open details → track → return. Include no results, failed requests, denied location, stale data, tomorrow’s service, long stop names and larger text.

Scope and limits

Inspected the local web app at phone widths (390px, with settings also at 320px) and a 1440px desktop layout, including light/dark appearance, stop/place search, route results, journey detail, settings, rendered accessibility trees and supporting source. Contrast ratios were calculated from the theme tokens using WCAG relative luminance.

This was a heuristic audit. Native iOS/Android, physical touch and software keyboards, real boarding/tracking, screen-reader operation, full offline behaviour and large-text reflow were not validated end to end. Location could not be established in the browser session, so the permission and recovery recommendations require device validation. Live data content may change. No application code was changed.
