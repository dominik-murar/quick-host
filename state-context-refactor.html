The short answer

The problem isn't the contexts, it's that state is stored where it's derived and shared where it's local. Almost every symptom traces to one of those two.

shouldIncrementStreak is derived from a date but kept in state — that's the infinite write loop. currentUnitData is global but only ever used by one route subtree — that's why clearUnitData() has to exist. The exercise route holds 15 useState calls, three of which are mutually exclusive by exercise type, so nothing stops an impossible combination compiling.

Three layers fix it: pure domain functions that don't know about React, two contexts split by lifetime rather than by data source, and routes as orchestrators. The exercise route goes from 623 lines to roughly 80.

What's actually wrong

Five structural problems, each with its own fix

1

Derived state stored as state

shouldIncrementStreak is a pure function of lastExerciseDate and today's date, but it lives in useState and is written by an effect that also performs a Firestore write. Because the effect depends on userData and its setUserData always allocates a fresh object, it re-triggers itself forever once the date is stale.

Storing it is what makes the loop possible. A function can't loop.

FirebaseProvider.tsx:147-168 — one effect that both derives a boolean and mutates the database.
2

One provider owning four unrelated things

FirebaseProvider is 204 lines covering: the user profile, lesson progress, the streak, unit content, the AsyncStorage cache, and two loading flags. Nothing in it needs to know about anything else in it.

The tell is clearUnitData(). Unit content is global state with a route-shaped lifetime, so the Home screen has to manually reset it on focus. If it were owned by the unit route it would unmount on its own and that function would not exist.

index.tsx:31-34 — Home runs a useFocusEffect whose only job is to clean up state belonging to a different screen.
3

A child provider mutating its parent

AuthProvider exposes setInitializing, and FirebaseProvider — its child — calls it in three places. So auth's readiness is decided by whether a Firestore read finished, and the dependency runs upward.

It also means "initialising" and "loading" are two separate booleans that must agree. Nothing enforces that, and both can be wrong at once.

FirebaseProvider.tsx:34, 144, 165, 167 — four references to a setter that belongs to the provider above it.
4

Impossible states are representable

The exercise route keeps three nullable data slots — wordsExerciseData, sentencesExerciseData, storiesExerciseData — of which exactly one is ever non-null. The type permits all eight combinations. The render path compensates with guards like exerciseType === "words" && wordsExerciseData, which is the type system being re-implemented by hand at runtime.

Same shape at the session level: user and userData are independently optional, so "signed in but no profile" and "profile but signed out" both typecheck.

[exerciseType].tsx:74-95 — three mutually exclusive slots plus four more per-type state atoms in one scope, separated only by comments.
5

A state machine spread across four switches

buttonAction is a six-value union driving a genuine state machine, but its transitions and its presentation are scattered: four separate switch statements over the same union, at lines 287, 301, 438 and 456, plus an isButtonDisabled function branching on exercise type.

Adding a state means finding all five. Two of them already disagree — "failed" renders the wrong-answer text but, until last week, took the neutral button colour.

[exerciseType].tsx — buttonText, buttonType, handleSentencesQuestionsButtonPress, handleStoriesButtonPress.

Proposed structure

Three layers, each with one job

1 · Domain — pure functions, no React

domain/streak.ts · domain/progress.ts · domain/exercise.ts

Every rule that is currently tangled with an effect or a Firestore call becomes a plain function of its inputs. No hooks, no mocks, trivially testable — which matters most for the streak, where the bugs actually are.

2 · Data — repositories, no React

data/userRepository.ts · data/unitRepository.ts

Firestore and AsyncStorage access as flat async functions. Today getUnitData interleaves cache reads, a network fetch, a progress backfill and three setState calls in one function; splitting them means each can be read on its own.

3 · Contexts — split by lifetime, not by data source

SessionProvider (app-wide) · UnitProvider (per unit route)

Session owns auth and profile as a single discriminated union, replacing AuthProvider plus half of FirebaseProvider and both loading flags. Unit is mounted by the unit route layout, so unit content lives exactly as long as the screens that use it — no global slot, no manual clearing.

ThemeProvider and SpeechProvider stay as they are; they are already single-purpose.

Session as one union

Four booleans and two optionals become one value

Now

// FirebaseProvider

// 2^4 x 2 x 2 nominal combinations,
// ~4 of them legal

Proposed

export type Session =
  | { status: "loading" }
  | { status: "signedOut" }
  | { status: "ready"; user: User; profile: Profile };

// Consumers destructure once and the compiler
// guarantees the rest:
const session = useSession();
if (session.status !== "ready") return <Loading />;
session.profile.streak  // no optional chaining

The streak then reads off profile, and shouldIncrementStreak is replaced by a function call at the point of use.

The streak, as a pure function

This is the fix for the infinite loop, and it removes the state entirely

// domain/streak.ts — no React, no Firestore, no clock reads
export type StreakState = "countedToday" | "continues" | "broken";

export const streakState = (lastExerciseDate: string, today: string): StreakState => {
  if (lastExerciseDate === today) return "countedToday";
  if (lastExerciseDate === previousDay(today)) return "continues";
  return "broken";
};

// The only place a streak number is produced.
export const nextStreak = (current: number, state: StreakState): number =>
  state === "countedToday" ? current : state === "continues" ? current + 1 : 1;

Two things fall out of this for free:

  • The loop cannot happen. Nothing writes to the database while deriving, so there is no effect to re-trigger. The reset stops being a side effect and becomes part of nextStreak returning 1.
  • Day one works. "broken" yields 1, not 0 + 1 gated on a flag, so a brand-new account scores on its first exercise — the second streak bug, fixed by the same three lines.

And it is testable without a single mock: three input pairs cover every branch.

The remount is the part worth stealing

That 40-line reset effect exists only because the component outlives the thing it represents. Giving the round its own component and a key deletes the effect outright — React discards the state for you. It is the single largest readability win here per line changed, and it removes a whole class of "stale state from the previous round" bug.

The button machine as a table

Four switches become one lookup

  end:     { textKey: "common.buttonSuccess",  variant: "success", next: "leave" },

The "failed" row is the argument for this shape: text and colour disagreeing was possible precisely because they were decided in two different switches.

The route as an orchestrator

Your CLAUDE.md asks for a top-level handler whose structure explains itself

// app/.../[exerciseType].tsx — the whole route
const ExerciseScreen = () => {
  const { unitId, lessonId, kind } = useExerciseParams();
  const session = useSession();
  const lesson = useLesson(unitId, lessonId);

  if (session.status !== "ready") return <LoadingScreen />;
  if (!lesson) return <LoadingScreen />;

  return <ExerciseRound key={lesson.roundKey} kind={kind} lesson={lesson} />;
};

Everything else moves behind three names — useExerciseParams, useLesson, ExerciseRound — and the per-kind logic sits in useWordsRound / usePromptRound / useStoryRound, each owning only its own state. The route reads as a sentence; no section comments needed, because nothing unrelated shares the scope.

What this deletes

The clearest measure of whether it worked

shouldIncrementStreak clearUnitData() setInitializing initializing loading unitDataLoading the 40-line reset effect 3 nullable data slots 4 switch statements getUserUnitData() guards

getUserUnitData is worth calling out: it exists because UserData is a Record mixing _meta, activity and per-unit progress under one index signature, so every read needs a runtime narrowing helper. Splitting progress into its own field removes the helper and the "streak" in value sniffing with it.

Against your stated preferences

Simple solutions, not grandiose piles

Net effect is subtraction: no state library, no new abstractions beyond three plain files and one extra context. The two biggest wins — a remount key and a lookup table — are both smaller than what they replace.

Readable to the point comments are unnecessary

The current exercise route needs // Words exercise state, // Stories exercise state, // Button state. Those comments are load-bearing because unrelated things share one scope. Split by kind and they become redundant.

Top-down modular; the handler orchestrates

Right now the route is state at the top, handlers around line 320, JSX at 540. Inverted. Afterwards the first function is the whole story in eight lines.

Less mainstream data structures where they earn it

You already use Map and Set well for word pairs and matches — kept as-is. The addition is discriminated unions, which is the same instinct applied to control flow: make the wrong state unrepresentable rather than guarding against it.

Typesafe, no any

No any anywhere today, so this is about the weaker failure: types that permit nonsense. Both unions above remove whole families of impossible values, and getUserUnitData's runtime narrowing disappears.

Tests useful, but don't test types

Layers 1 and 2 are plain functions, so the tests worth having become cheap: streak transitions, progress math, answer checking. No provider mounting, no Firestore mocks, and nothing asserting on shapes the compiler already guarantees.
